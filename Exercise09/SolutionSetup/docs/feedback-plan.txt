FEEDBACK PLAN
=============

Positive feedback (keep as is)
- Comments are extensive and make the code easy to follow.
- Clear structure (UI - Vehicles - Garage), short helper methods, partial classes.
- Sample-vehicle populate solution, good tests, no crashes found.
- Clear menu with one command per option and clear prompts.

Phase 1: Garage and model cleanup (code separation)
- Have a GarageHandler class that handles the menu and user input, so there is a handler between the UI and the Garage. It should implement a IHandler interface with methods for each menu option, so the UI can be tested without Console input/output.
- Make Populate() use the message returned by AddVehicle() and report why each vehicle was not parked
  (instead of only "Parked 0 of 3 vehicles.").
- Make vehicle properties immutable after construction (private/init set) so values cannot be changed
  after a vehicle is parked.


Phase 2: Vehicle validation, error handling and tests for all vehicle types
- Truck: add a valid range for capacity (kg), not only "not negative", to block ridiculous numbers.
- Boat: add a lower limit (and sensible upper limit) for length; it can currently be negative.
- Motorcycle, Airplane, Bus, Boat: validate all values (e.g. no negative engines, cylinder volume,
  seats, etc.).
- Car color: decide whether colors should be limited to a fixed list or allow any valid color,
  and document the decision.
- Use clear error messages that include the valid range and unit.
- Add tests for each vehicle type: valid values, boundary values (min/max), and invalid values
  (negative, zero, too large).
- Add tests for immutability of properties after construction.
- Add tests for Garage.Populate() failure messages.

Phase 3: Remove duplicated vehicle type definitions
- Vehicle types are currently listed in four places: the enum, park menu text, the switch in
  ParkVehicle, and the search text.
- Build menu and search text from the enum (Enum.GetValues) so they always match.
- Reduce the switch to a single place (e.g. a factory) so adding a new type needs minimal changes.
- Add tests that verify the menu/search text contains every enum value.

Phase 4: UI input handling and user flow
- Validate each answer immediately and ask again on invalid input (e.g. invalid vehicle type such as
  9 is rejected right away, before the other parameters are prompted).
- On invalid input, re-prompt instead of returning to the main menu.
- Show valid ranges in prompts and error messages (e.g. capacity "1-1000", and handle numbers too big
  for an int with a range message).
- Add an empty line or "Press Enter to continue" after each result so the result is not missed
  when the menu is shown.
- Populate garage: show a message such as "Sample vehicles are already added" when used a second
  time, or remove/disable option 2 after use.
- Add UI tests for re-prompting, range messages and the populate-twice case.

Phase 5: Search changes (last)
- Rework the search flow so users do not need to step through every property one at a time.
  Options: choose which properties to filter on first, or enter criteria in one line.
- Keep the design extensible so new vehicle properties do not make the search longer to use.
- Add or update tests for the new search flow.

Order rationale
- Phases 1-3 fix the model, validation and duplication first, so the UI in Phases 4-5 can build on
  stable behavior.
- UI and search changes are saved for last.
